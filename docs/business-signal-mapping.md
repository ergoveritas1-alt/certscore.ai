# Business Signal Mapping

This document maps business-facing signal categories to the actual snapshot fields collected by the scanner and flags where business copy is stronger than the implementation.

## Scope

- Canonical source of truth: `ScanSnapshot` fields assembled in the scanner snapshot pipeline.
- Secondary compatibility layer: a reduced `scan_signals` projection used for UI/history compatibility.
- Interpretation rule: if a statement implies verified compliance behavior, legal sufficiency, or operational fulfillment, it is too strong unless the scanner directly tests that behavior.

## Notes on Strength of Claims

- Avoid saying the scanner "honors" privacy rights.
  - Current implementation detects visible request paths and public disclosures, not request fulfillment.
- Avoid saying the scanner verifies "compliance."
  - The implementation collects signals and computes heuristic scores.
- Avoid implying "identity tools" coverage is comprehensive.
  - Current coverage is partial and signature-based.
- Avoid implying accessibility results are equivalent to manual audit outcomes.
  - Current implementation is centered on automated rule counts and heuristic scoring.
- Avoid implying security coverage includes vulnerabilities.
  - Current implementation measures posture, metadata, and disclosure signals, not exploitability.

## Implementation Notes

- The most complete field set lives in the snapshot schema, not in the compatibility `scan_signals` table.
- Some snapshot fields are direct detections, while others are derived scores or heuristics.
- Several business-useful fields exist beyond the original five-bucket wording, especially around subscription, affiliate, advertising, transparency, and change-detection signals.
