## Configuration boundary

`scripts/deploy-fast.ts` ordinarily calls `applyScannerRuntimeConfiguration()` before image promotion and calls it again with coverage enabled afterward. Those calls can update memory, identity settings and action/coverage flags. Its existing image-provenance transaction also clears and writes `SCANNER_IMAGE_DIGEST` through Lambda environment updates. Therefore the current scanner deploy flow is not a configuration-preserving image release.

The new `--preserve-scanner-configuration` option refuses a real `all` or `scanners` deployment before Git resolution, push, preflight or AWS work. `--no-push`, an explicit ref and skipping preflight cannot bypass this refusal. Local plan/dry-run handling remains available; consumer-only modes retain their existing behavior. The option does not turn legacy deployment into a configuration-free promotion, and omission does not grant permission to change settings.

Before a producer release under restricted settings scope, a provenance-only promotion path must omit the identity/coverage configuration calls while retaining the existing revision-guarded provenance transaction and verifying existing worker settings. The existing `synchronizeScannerImage` helper preserves unrelated environment values, but the surrounding `deploy-fast` flow still applies broader settings. A future authorization must expressly cover the exact image promotions and the necessary `SCANNER_IMAGE_DIGEST` writes; the current cost approval covers neither. Do not leave a stale digest to evade this boundary. `repair-scanner-image-provenance.ts` is not an image promoter and performs AWS reads even without `--apply`; it was not executed here.
