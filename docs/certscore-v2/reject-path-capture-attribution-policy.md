# Reject-path capture and attribution repairs

CertScore.ai retains observed request and write facts through the existing
producer -> verified retained packet -> typed assessment -> normalized concern
-> concern policy -> unified finding/checklist -> score flow. These repairs add
no deduction rule or weight. Semantic refusal registration remains separate.

## Bounded capture

Only the Reject attribution graph reserves half its existing node, edge,
stack, correlation and byte allowances before dispatch. The verified dispatch
callback releases the remainder without marking consent confirmed. Final
ExtraInfo/cookie correlation prioritizes retained post-click request chains.
The existing global caps remain unchanged. Skipped pre-click graph details
remain explicitly limited; graph reservation cannot recover previously omitted
facts or establish complete browser coverage. Main-page request evidence and
other passive lanes remain independent. Accept and GPC capture are unchanged.

Unconfirmed Reject paths replace their existing terminal write read with the
same read plus bounded hook/readback metadata. `after_action_write_diagnostics.v1`
retains lifetime/ring/readback loss, hook health, document-match and exact
observed/retained window counts. Metadata is optional and diagnostic-only;
missing metadata remains unknown. Retain classified non-essential writes before
CMP/unknown chatter within the existing 48-row cap and 96-row readback. The
192-record in-page ring, hook scope and observation windows are unchanged.
These records do not prove exact write identity/value, registered refusal,
continuous instrumentation, other frames/APIs or score eligibility.

Origin/partition event diagnostics bind to the resolved, authorized action
origin before dispatch. A rebind recomputes bounded retained origin flags only
when no valid events were omitted. Omitted origins or a frozen capture prevent
rebinding and retain an explicit limitation. Receipt-clock events keep their
existing diagnostic-only status and lack of renderer document/write attribution.
Never promote these receipts into canonical writes or deductions.

## Canonical endpoint attribution

The canonical vendor registry recognizes the exact legacy Heap `/h` collector
and the HubSpot `__ptc.gif` variant alongside the existing tracking-pixel rules.
These establish analytics service activity; they do not prove persistent
identifier transmission, a complete payload, successful refusal or a deduction.
Shopify's exact Monorail collector receives neutral mixed-telemetry attribution.
Its URL alone does not resolve analytics versus operational purpose. A
first-party proxy-like path alone does not establish Shopify ownership.

Use explicit producer replays over checksum-verified retained request facts for
internal evaluation. Bind original and derived packet hashes, resolver version
and changed classifications in a replay receipt. Never change original bytes,
silently reclassify stored packets on read, infer redacted identifiers or upgrade
confidence from vendor documentation. Production reports and historical scores
are not regenerated by an internal replay.

## Budgets and validation

No new browser round trip, browser run, lane, model call, request inventory cap,
write cap, observation timeout, publication wait or retention is introduced.
Expected incremental bounded CPU/metadata is below $0.50/month at 100,000 scans
under existing retention. Production deployment requires separate authorization.

Regressions cover precise endpoint matching and neutral mixed-purpose handling,
pre-click graph floods with post-click request/cookie correlation, healthy native
browser behavior, unconfirmed writes behind CMP chatter, missing/malformed
metadata, resolved-origin rebinding, overflow/frozen diagnostics, historical
capture compatibility and the canonical source/assessment/concern/score flow.
