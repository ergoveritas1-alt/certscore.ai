# WC01 v2 row allowlist design

Status: design only. Do not implement normalized concern mapping from this document without a separate implementation pass.

## Current state

The current v2 to WC01 path is intentionally internal:

```text
V2ReportProjectionDraft
-> Wc01V2ShadowProjection
-> internal preview
```

`Wc01V2ShadowProjection` artifacts are diagnostic only. They are generated by `pnpm v2:wc01-shadow`, consume `V2ReportProjectionDraft` outside the web app, and are not wired into production report behavior.

WC01 also has a platform-admin shadow preview at:

```text
/app/admin/v2-shadow-preview?artifact=artifacts/.../Wc01V2ShadowProjection.json
```

The preview requires `CERTSCORE_V2_SHADOW_PREVIEW_ENABLED=1`, reads only `Wc01V2ShadowProjection.json`, and fails closed on unsupported contract versions, `productionEligible: true`, any `topFindingEligible: true`, any `gapEligible: true`, a forbidden `gap_observed` token, or raw blocked evidence fields.

All shadow output remains hard-false for:

- `productionEligible`
- `topFindingEligible`
- `gapEligible`

There is no v2 production UI integration, report-card integration, checklist integration, executive-summary integration, top-finding integration, scoring integration, regulatory-lens integration, or normalized-concern mapping.

## Future mapping principle

The future path, if approved, should be:

```text
Wc01V2ShadowProjection
-> explicit row allowlist
-> normalized concern candidate drafts
-> concern policy
-> unified findings/checklists
```

V2 rows may enter WC01 only as normalized concern candidate drafts. They must not feed report cards, checklist builders, executive findings, top findings, regulatory lenses, scoring, or unified findings directly.

The row allowlist must be explicit and typed. Each allowed row needs evidence gates that inspect status, source modules, evidence refs, display-safe excerpts, confidence, directness, vendor purpose, missing corroborators, and demotion reasons before producing any normalized concern draft.

Concern policy remains responsible for final promotion eligibility, external surfacing eligibility, allowed narrative tier, negative evidence flags, and unified finding projection. The bridge may propose a target concern or suggested unified finding ID, but it must not decide final checklist status, report lane, executive inclusion, or top-finding eligibility.

No v2 row maps directly to `gap_observed`. No bridge output should use legal-conclusion language or customer-facing determinations.

## Proposed row tiers

### Tier A: possible future normalized concern candidates

These rows may be candidates for a future allowlist only when all row-specific evidence gates pass:

- `third_party_vendors_observed`
- `pre_consent_tracking_detected`
- `third_party_cookie_pre_consent`
- `consent_banner_observed_or_not_observed`
- `session_replay_or_behavioral_analytics_observed`

Tier A means "eligible for bridge evaluation", not "eligible for report surfacing." A passing bridge row should produce only a normalized concern candidate draft. Concern policy still decides whether the resulting concern is eligible, audit-only, review-only, blocked, or suppressed.

### Tier B: review-only or internal diagnostic for now

These rows should not map into normalized concerns in the first bridge implementation:

- unresolved endpoint review
- `policy_runtime_vendor_alignment_review_signal`
- accept/reject consent-flow deltas, including `accept_reject_runtime_delta_observed`
- post-reject persistence or suppression rows
- accept-only vendor/cookie delta rows
- assisted or Nano-only candidates
- privacy-policy, cookie-policy, privacy-choice, or policy-surface observed/not-observed rows when the policy-surface module did not run, failed, was partial, or lacks direct display-safe evidence

These rows are useful for calibration, reviewer triage, and future policy design. They should remain `review_signal`, `coverage_limitation`, `not_testable`, or internal diagnostic until separate gates prove they can be mapped without overclaiming.

### Tier C: never tracker-supporting by default

Rows or vendor observations dominated by these purposes must not support tracker findings by default:

- security
- performance_monitoring
- customer_support
- CDN/static
- site-owned infrastructure
- fraud-prevention
- bot-defense
- RUM
- live-chat
- consent_management
- tag_management without consent or tracking context
- unknown infrastructure-only observations

These purposes may be retained as diagnostic context, coverage context, or vendor inventory context. They must not create tracker, consent-timing, disclosure-gap, or policy/runtime-alignment concerns unless a separate evidence gate proves an allowed tracker purpose and concrete collection behavior.

## Tier A evidence gates

The gates below are proposed minimums for a future bridge. Missing, partial, skipped, failed, or not-testable source modules must fail closed.

### `third_party_vendors_observed`

- Required `sourceFindingKey`: `third_party_vendors_observed`
- Required source modules: pre-consent runtime scanner; vendor resolver
- Required status: `observed`
- Required evidence families: direct runtime request, script, iframe, cookie, or storage observation with a source ref; at least one resolved vendor with non-infrastructure purpose
- Minimum confidence/directness: high or medium confidence; `direct` preferred; inferred-only rows require a separate review-only path
- Required display-safe excerpts: at least one bounded excerpt identifying host/path, cookie name, script host, iframe host, or redacted request evidence
- Required source refs: at least one source ref ID and at least one excerpt ID
- Disallowed demotion reasons: `review_signal_only`, `coverage_limitation_present`, `source_module_missing_or_incomplete`, `non_tracker_purpose_only`, `library_only_without_collection`
- Disallowed missing corroborators: `runtime_source_ref`, `display_safe_excerpt`, `resolved_vendor`, `tracker_purpose`
- Allowed vendor purposes: advertising, analytics, session_replay, marketing_automation, advertising_measurement, identity_resolution, social_pixel, retargeting, tag_management only when paired with tracker purpose evidence
- Blocked vendor purposes: security, performance_monitoring, customer_support, CDN/static, site-owned infrastructure, fraud-prevention, bot-defense, RUM, live-chat, consent_management, unknown
- Possible normalized concern target: tracker or third-party runtime vendor inventory review concern; if no existing concern is appropriate, create a draft concern key rather than reusing a disclosure-gap or pre-consent finding
- Top-finding eligibility later: no direct eligibility from the bridge. It can become top-finding eligible only after concern policy, unified finding projection, surfacing policy, and top-finding policy independently allow it.

### `pre_consent_tracking_detected`

- Required `sourceFindingKey`: `pre_consent_tracking_detected`
- Required source modules: pre-consent runtime scanner; vendor resolver; consent-state attribution from scan-core
- Required status: `observed`
- Required evidence families: pre-consent network, cookie, storage, script, iframe, or collection endpoint evidence from the baseline/pre-choice phase
- Minimum confidence/directness: high confidence or strong medium with direct runtime evidence; `directVsInferred` must be `direct` or equivalent direct runtime classification
- Required display-safe excerpts: at least one bounded pre-consent excerpt with consent state, host/path or cookie name, vendor purpose, and redacted display value where applicable
- Required source refs: at least one source ref ID and at least one excerpt ID
- Disallowed demotion reasons: `review_signal_only`, `missing_concrete_preconsent_artifact`, `missing_preconsent_sequence_evidence`, `coverage_limitation_present`, `source_module_missing_or_incomplete`, `library_only_without_collection`
- Disallowed missing corroborators: `pre_consent_runtime_event`, `consent_state_at_time`, `display_safe_excerpt`, `source_ref`, `tracker_purpose`
- Allowed vendor purposes: advertising, analytics, session_replay, marketing_automation, advertising_measurement, identity_resolution, social_pixel, retargeting
- Blocked vendor purposes: security, performance_monitoring, customer_support, CDN/static, site-owned infrastructure, fraud-prevention, bot-defense, RUM, live-chat, consent_management, tag_management-only, unknown
- Possible normalized concern target: existing pre-consent tracking concern leading to `preconsent_tracking` or `pre_consent_tracking_detected`, subject to concern policy
- Top-finding eligibility later: possible only through separate concern policy, unified finding surfacing, evidence-contract, and top-finding eligibility checks

### `third_party_cookie_pre_consent`

- Required `sourceFindingKey`: `third_party_cookie_pre_consent`
- Required source modules: pre-consent runtime scanner; cookie snapshot or Set-Cookie capture; vendor resolver when vendor attribution is claimed
- Required status: `observed`
- Required evidence families: third-party cookie or storage evidence observed before a recorded consent choice; cookie name/domain/path or storage key must be display-safe and redacted as needed
- Minimum confidence/directness: high confidence direct cookie/storage evidence; inferred vendor purpose alone is not enough
- Required display-safe excerpts: at least one bounded cookie/storage excerpt with cookie name or storage key, host/domain, consent state, and redacted value context
- Required source refs: at least one source ref ID and at least one excerpt ID
- Disallowed demotion reasons: `review_signal_only`, `missing_concrete_preconsent_artifact`, `strictly_necessary_storage_only`, `coverage_limitation_present`, `source_module_missing_or_incomplete`
- Disallowed missing corroborators: `cookie_name`, `cookie_domain`, `consent_state_at_time`, `display_safe_excerpt`, `source_ref`
- Allowed vendor purposes: advertising, analytics, session_replay, marketing_automation, advertising_measurement, identity_resolution, social_pixel, retargeting
- Blocked vendor purposes: security, performance_monitoring, customer_support, CDN/static, site-owned infrastructure, fraud-prevention, bot-defense, RUM, live-chat, consent_management, strictly necessary, unknown
- Possible normalized concern target: existing pre-consent cookie/storage concern leading to `third_party_cookie_pre_consent`, subject to concern policy
- Top-finding eligibility later: possible only through separate policy and evidence-contract checks

### `consent_banner_observed_or_not_observed`

- Required `sourceFindingKey`: `consent_banner_observed_or_not_observed`
- Required source modules: pre-consent runtime scanner; consent UI observation; Nano UI assist if consent profile ran
- Required status: `observed`, `checked`, or `not_observed`; `coverage_limitation`, `not_testable`, and `assisted_candidate` fail closed
- Required evidence families: direct consent surface observation, absence observation, or bounded UI screenshot/DOM excerpt with scan phase and page URL
- Minimum confidence/directness: direct UI observation; Nano-only classification without scanner evidence remains review-only
- Required display-safe excerpts: at least one bounded UI/control excerpt or screenshot artifact ref for observed surfaces; for not-observed, a bounded scan-scope/control-search summary is required
- Required source refs: at least one source ref ID; excerpt ID required when text/control evidence exists
- Disallowed demotion reasons: `review_signal_only`, `source_module_missing_or_incomplete`, `consent_surface_unstable_or_not_evaluable`, `prior_consent_or_suppressed_banner_suspected`, `shallow_consent_control_search_scope`
- Disallowed missing corroborators: `consent_ui_observation`, `scan_scope`, `source_ref`
- Allowed vendor purposes: not applicable for banner existence; CMP vendors may be diagnostic but should not create tracker concerns
- Blocked vendor purposes: all tracker purposes as primary support for banner-existence concerns; banner mapping should use UI evidence, not runtime vendor inventory
- Possible normalized concern target: consent surface present/absent review concern, potentially `consent_surface_missing` only through concern policy and only when absence evidence is strong
- Top-finding eligibility later: no direct eligibility from the bridge; possible only if concern policy and surfacing policy independently promote a consent-surface concern

### `session_replay_or_behavioral_analytics_observed`

- Required `sourceFindingKey`: `session_replay_or_behavioral_analytics_observed`
- Required source modules: pre-consent runtime scanner; vendor resolver; journey/endpoint classification when collection behavior is claimed
- Required status: `observed`
- Required evidence families: direct session-replay or behavioral analytics collection endpoint, cookie/storage signal, script plus collection endpoint, or strong vendor observation with behavior `session_replay_collection_observed`
- Minimum confidence/directness: high confidence direct evidence for collection claims; library-only evidence remains review-only unless paired with collection endpoint evidence
- Required display-safe excerpts: at least one bounded excerpt showing vendor/host/path, behavior category, consent state, and redacted request/cookie context
- Required source refs: at least one source ref ID and at least one excerpt ID
- Disallowed demotion reasons: `review_signal_only`, `library_only_without_collection`, `coverage_limitation_present`, `source_module_missing_or_incomplete`, `missing_runtime_request_url_evidence`
- Disallowed missing corroborators: `session_replay_collection_observed`, `source_ref`, `display_safe_excerpt`, `resolved_vendor`
- Allowed vendor purposes: session_replay, behavioral_analytics, analytics only when session-replay collection behavior is separately observed
- Blocked vendor purposes: performance_monitoring, customer_support, security, CDN/static, RUM-only, live-chat-only, unknown, tag_management-only
- Possible normalized concern target: existing session replay or behavioral analytics concern leading to `session_replay_observed`, `session_recording_services_detected`, or a review-only session replay concern, subject to concern policy
- Top-finding eligibility later: possible only through separate policy, and only with direct collection evidence plus existing session-replay evidence contracts

## Explicit non-goals

- No direct report-card integration
- No direct checklist integration
- No direct executive-summary integration
- No direct top-finding integration
- No direct scoring or regulatory-lens integration
- No direct unified finding creation
- No direct `gap_observed` mapping
- No legal conclusions
- No customer-facing vendor claims from unresolved endpoint review
- No use of `V2ReportProjectionDraft` inside the WC01 web app
- No bypass around normalized concerns, concern policy, or existing finding evidence contracts

## Risk register

- WC01 status semantic mismatch: v2 `observed` means evidence observed, not regulatory gap observed.
- Review-signal promotion drift: `review_signal` rows could accidentally become checklist rows if the bridge treats assessment status as production status.
- Observed-as-gap drift: checklist builders contain `Gap observed` statuses, but v2 bridge rows must never set them directly.
- Vendor display overreach: named vendors from runtime observation could become customer-facing claims without policy gates and evidence-contract checks.
- Policy/runtime alignment overclaiming: alignment rows could be mistaken for disclosure gaps even though current v2 output treats them as conservative review signals only.
- Consent-flow overclaiming: reject/accept deltas could be treated as failures when reject action confidence, accept action confidence, baseline comparability, or post-action timing is incomplete.
- Non-tracker purpose leakage: security, performance monitoring, support, fraud-prevention, bot-defense, RUM, live-chat, CDN, and site-owned infrastructure could be pulled into tracker concerns.
- Raw evidence leakage: raw cookie values, request bodies, sensitive query values, full DOM text, full policy text, or unredacted URLs could enter normalized concern raw evidence.
- Top-finding accidental promotion: bridge candidates could carry language or flags that imply executive/top-finding eligibility before policy review.
- Coverage limitation collapse: failed or partial modules could be treated as negative evidence or proof of absence.
- Nano overreach: Nano-assisted candidate labels could be treated as direct observed evidence.

## Recommended implementation sequence

1. Add a typed allowlist config in `@certscore/report-adapter` or a new internal bridge module.
2. Keep the first bridge output as normalized concern candidate drafts only, not production concerns.
3. Add fixtures based on saved `Wc01V2ShadowProjection.json` artifacts.
4. Write tests proving every Tier A gate fails closed when any required module, status, excerpt, source ref, confidence, directness, or vendor-purpose condition is missing.
5. Add an aggregate allowlist dry-run CLI that reads WC01 shadow batches and reports candidate counts, blocked counts, and block reasons.
6. Compare dry-run output across expanded and stress fresh-registry cohorts.
7. Review all Tier B and Tier C rows that would have mapped but were blocked.
8. Only after dry-run review, consider a separate production integration proposal that feeds approved bridge output into normalized concern construction and concern policy.

## Future test plan

- Allowlisted Tier A rows map only when all gates pass.
- Rows with missing, partial, skipped, failed, or not-testable source modules fail closed.
- Tier B review-only rows never map.
- Tier C non-tracker purposes never map to tracker concerns.
- Bridge output never emits or contains `gap_observed`.
- Bridge output never sets top-finding eligibility.
- Bridge output never imports production checklist, executive, report-card, regulatory-lens, or top-finding components.
- Bridge output never includes raw blocked fields.
- Policy/runtime rows remain review-only diagnostics.
- Consent delta rows require confident direct reject and accept comparison before any future concern draft is considered.
- Status copy remains review-signal language and does not imply legal conclusions.
- Vendor names stay internal unless concern policy, evidence contracts, and display projection separately approve them.
